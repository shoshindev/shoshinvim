# ShoshinVim distribution specification

- Status: planned release and installation contract
- Product binary: `shoshinvim`
- Scope: standalone terminal application; Neovim is a target and validation dependency, not the host process
- Snapshot: 2026-09-28

No release currently exists. Commands in this document are the required future interface and must not be advertised as live until the corresponding signed release assets are published.

## 1. Decision

ShoshinVim should ship as a self-contained native executable with prebuilt release archives.

The recommended installation strategy is:

1. **Homebrew tap** `[RECOMMENDED for macOS and Homebrew users]` — clean upgrades, ownership, and uninstall.
2. **HTTPS shell installer** `[RECOMMENDED quick start for macOS/Linux]` — lowest-friction bootstrap on a bare system.
3. **Direct release archive** `[RECOMMENDED for verification/offline/manual environments]` — explicit artifact and checksum handling.
4. **PowerShell installer** `[RECOMMENDED quick start for Windows]`.
5. Additional native package channels as the project matures.

`curl | sh` is therefore a good primary onboarding command, but not a sufficient distribution strategy by itself.

## 2. Planned install commands

After the canonical release repository and assets exist, the quick-start command is:

```sh
curl --proto '=https' --tlsv1.2 -LsSf \
  https://github.com/shoshindev/shoshinvim/releases/latest/download/shoshinvim-installer.sh | sh
```

Homebrew:

```sh
brew install shoshindev/tap/shoshinvim
```

Windows PowerShell:

```powershell
irm https://github.com/shoshindev/shoshinvim/releases/latest/download/shoshinvim-installer.ps1 | iex
```

Every quick command must be accompanied by:

- a link to inspect the installer before running it;
- version-pinned command examples;
- direct archive and checksum instructions;
- supported platform/architecture list;
- update and uninstall instructions.

## 3. Release artifacts

Each tagged release publishes:

- one archive per supported platform and architecture;
- `shoshinvim-installer.sh`;
- `shoshinvim-installer.ps1`;
- `SHA256SUMS`;
- build-provenance attestations;
- software bill of materials when release tooling supports it reliably;
- shell completions and man page, either embedded/generated by the binary or included in platform packages;
- release notes with breaking changes and migration instructions.

Initial targets:

| Platform | Architecture | Initial support |
| --- | --- | --- |
| macOS | Apple Silicon (`aarch64`) | Required |
| macOS | Intel (`x86_64`) | Required while CI/toolchain support remains practical |
| Linux glibc | `x86_64` | Required |
| Linux glibc | `aarch64` | Required |
| Windows | `x86_64` | Required |
| Windows | `aarch64` | Add when the dependency/toolchain matrix is verified |
| Linux musl | `x86_64`, `aarch64` | Add after runtime and terminal testing |
| NixOS | supported package/flake | Do not route through the generic shell installer |

Archives use stable names containing product, version, target triple, and extension. The executable inside is always named `shoshinvim` or `shoshinvim.exe`.

## 4. Shell installer contract

The shell installer must:

1. require HTTPS and fail on HTTP/TLS/download errors;
2. detect supported OS and architecture without sending extra telemetry;
3. resolve a tagged release and then download only versioned assets;
4. download into a private temporary directory;
5. verify the archive against the published SHA-256 manifest before extraction;
6. install only the expected executable and optional completion/man-page assets;
7. create an install receipt recording version, source, path, checksum, and timestamp;
8. avoid `sudo` and system directories by default;
9. avoid modifying shell startup files without an explicit option;
10. print exact PATH instructions when the selected directory is not already available;
11. leave existing binaries untouched if verification or replacement fails;
12. never start ShoshinVim, Neovim, plugin installation, or configuration generation as an installer side effect.

Default install-directory order:

1. explicit `--install-dir`;
2. `$SHOSHINVIM_INSTALL_DIR`;
3. `$XDG_BIN_HOME` when set;
4. `$HOME/.local/bin`.

The installer supports:

```text
--version <tag>
--install-dir <path>
--no-modify-path
--force
--help
```

Piped arguments use `sh -s --`, for example:

```sh
curl --proto '=https' --tlsv1.2 -LsSf <installer-url> \
  | sh -s -- --version v0.1.0 --install-dir "$HOME/.local/bin"
```

`--force` permits replacement of a script-managed ShoshinVim binary after verification. It does not permit replacing an unrelated file at the same path.

## 5. Verification and supply-chain requirements

Checksums protect against corruption and mismatched downloads. Build attestations additionally connect an artifact to the repository, workflow, and commit that produced it. Neither mechanism is marketed as proof that the software is vulnerability-free.

Release CI must:

- build from a protected tag;
- use locked dependencies;
- run tests on each supported target class;
- generate checksums after final packaging;
- generate provenance attestations for executable archives;
- publish draft releases only after all expected assets exist;
- prefer immutable releases once the workflow is stable;
- prevent a “latest” installer from selecting prereleases unless explicitly requested.

Manual verification documentation includes both:

```sh
shasum -a 256 -c SHA256SUMS
```

and, for users with GitHub CLI:

```sh
gh attestation verify <archive> --repo shoshindev/shoshinvim
```

The installer itself cannot require GitHub CLI, but it may verify an attestation when a supported verifier is present and the behavior is deterministic. Checksum verification remains mandatory.

## 6. Package-manager channels

### Homebrew

Maintain a `shoshindev/homebrew-tap` repository and publish a fully qualified formula:

```sh
brew install shoshindev/tap/shoshinvim
```

The formula installs prebuilt verified release archives, declares checksums, installs completions/man pages, and supports normal `brew upgrade` and `brew uninstall` flows.

### Windows

Start with the PowerShell release installer. Add WinGet and/or Scoop manifests after release automation, upgrade behavior, and Windows terminal testing are stable.

### Linux ecosystems

Direct archives and the shell installer are the initial baseline. Add Nix, Arch/AUR, Debian/RPM, or other packages only when someone owns their update and verification lifecycle. Do not publish abandoned first-party packages merely for a longer install list.

### Source installation

Source installation is a developer/unsupported-platform option, not the beginner path. If ShoshinVim is implemented in Rust, document `cargo install --locked` and consider `cargo-binstall`; if implemented in Go, document the version-pinned `go install` form. Users should not need a compiler for the normal installation path.

## 7. Release tooling

The distribution contract is implementation-language independent, but automation should be generated rather than maintained as several unrelated release scripts.

- For a Rust executable, `dist`/`cargo-dist` is the preferred first evaluation because it can generate shell, PowerShell, Homebrew, archives, and CI release workflows.
- For a Go executable, GoReleaser is the equivalent first evaluation.
- Either choice must be audited against this document; generated defaults do not override install paths, verification, receipt, or non-mutation requirements.

The implementation choice remains separate from the user-facing install contract.

## 8. Updates

`shoshinvim update` respects install ownership:

| Install source | Update behavior |
| --- | --- |
| Homebrew | Print and optionally invoke `brew upgrade shoshindev/tap/shoshinvim` after confirmation. |
| Script installer | Fetch metadata, show current/target versions and release notes, then download and atomically replace after verification. |
| Direct/manual archive | Show the exact release URL and verification steps; do not assume ownership. |
| Source install | Print the version-pinned source update command. |
| Unknown/package-managed | Identify the executable path and refuse self-replacement. |

There is no silent background self-update. A passive version check is opt-in, rate-limited, and reports only that an update exists.

## 9. Uninstall

`shoshinvim uninstall` removes only files listed in a valid ShoshinVim install receipt and only after confirmation.

It never removes:

- generated Neovim configuration;
- `.shoshinvim` state stored inside a managed configuration target;
- backups or recovery journals;
- Neovim plugins;
- language servers, formatters, linters, parsers, debuggers, or runtimes;
- user-owned Lua.

For package-manager installs, ShoshinVim prints the manager's uninstall command instead of deleting manager-owned files.

## 10. First run and target discovery

After installation, `shoshinvim` runs entirely outside Neovim.

Application preferences live at `$XDG_CONFIG_HOME/shoshinvim/config.toml` (with platform-equivalent defaults). Installer receipts and update metadata live under `$XDG_STATE_HOME/shoshinvim/`. These are distinct from the `.shoshinvim` ownership state stored inside a managed Neovim configuration target.

Target selection order:

1. `--config-dir <path>`;
2. `SHOSHINVIM_TARGET_DIR`;
3. platform Neovim config standard path derived from XDG/environment conventions;
4. an explicit interactive choice when discovery is ambiguous.

ShoshinVim launches even when `nvim` is absent so it can explain the missing dependency. Saving is blocked until a supported Neovim executable can validate the proposed configuration.

The first run does not install plugins or tools merely because the application itself was installed.

## 11. Acceptance criteria

Distribution is ready when:

- a clean macOS or Linux user can install one verified binary without a compiler or root privileges;
- Homebrew install, upgrade, and uninstall work through the tap;
- Windows has a verified PowerShell path;
- checksums fail closed when an archive is modified;
- release artifacts identify their version and target consistently;
- `shoshinvim --version` matches the release tag;
- terminal completions and man/help output are installed or generated correctly;
- update behavior respects install ownership;
- uninstall leaves generated Neovim configuration and tools untouched;
- failed installation or update leaves the previous executable usable;
- documentation never presents an unpublished command as working.
